# Read-only Playwright browser runtime

## Runtime boundary

The `playwright` repository skill accepts a public URL or a web-search question from the user's chat request. The chat agent queues the run in `awaiting_consent`; no worker container is dispatched until the owner approves that run on its owner-scoped result page. The approval file binds a random token to the run ID and owner ID and expires after five minutes if the worker has not consumed it. The host verifies that proof again before each browser request.

The optional handoff registry is process-memory state shared by Django threads, so the web service must run one process (`gunicorn --workers 1 --threads 4`). Do not increase the worker count without replacing the registry with an equivalently volatile cross-process mechanism. Handoff events and frames expire with their task; a Django restart drops them, and the browser fails closed if it can no longer authenticate the bridge.

The dedicated `skill-browser-worker` image contains the pinned upstream skill, Node.js, Playwright, and Chromium. Browser jobs use Docker `--network=none`, an unprivileged user, read-only root filesystem, no capabilities, no-new-privileges, and bounded CPU, memory, process count, runtime, request count, response size, and temporary storage. The browser job is capped at one CPU, 512 MiB memory, 128 processes, and 64 MiB temporary storage. A 64-process cap caused Chromium's page renderer to crash in controlled Docker Desktop runs; 128 is the tested cap that supports a page while remaining bounded. Chromium's nested sandbox is disabled because Docker Desktop's Linux host disables unprivileged user namespaces under AppArmor; the Docker container is the explicit isolation boundary. The worker receives no application credentials, session cookies, host network socket, or Docker socket. Do not relax Docker's default seccomp/AppArmor policy, capabilities, identity, network isolation, read-only root, or resource limits to enable Chromium's nested sandbox.

`BrowserContext.route` intercepts all HTTP(S) page and resource traffic. Service workers are blocked and WebSockets are closed. Only GET requests on port 80 for HTTP or 443 for HTTPS are accepted. The host mediator resolves each requested hostname, rejects any private or special address, and connects to one validated resolved address. The fixed adapter handles main-frame redirects one hop at a time: it validates the resolved `Location`, substitutes an inert page for that hop, and navigates to the validated next URL through the route, causing a fresh host request and DNS/private-address check without exposing a 3xx to Chromium. Redirect loops and chains over ten hops fail closed. Redirected subresources are blocked after their redirect response because fulfilling their content at the original URL could change relative-resource resolution. Other skills continue to use their existing per-request policy.

For a URL task, the initial workflow does not click links, fill forms, authenticate, submit data, or perform external actions. JavaScript is disabled. The worker returns extracted page text and citations collected only from successfully fulfilled main-frame navigations. Citations are shown on the owner-only skill result page and added to the originating chat reply when the owner opens that result; page instructions cannot expand the task. A public GET can still have meaning on a remote site beyond viewing content. This slice rejects non-GET requests and private/special destinations but does not classify all site-specific payment, card, or other state-changing GET URLs; treat this as a remaining limitation before expanding availability.

## Search-to-answer path

Search approval discloses the query, Mwmbl and its CC BY-NC-SA 4.0 license, and the exact selected chat model route that will receive excerpts from pages the browser opens. The host calls Mwmbl through the mediator and shared SQLite limiter, then supplies at most five validated public destinations to the browser. It follows safe main-frame redirects. From successfully opened search-result pages, it reads at most 20 anchor targets per page and ranks their visible labels by overlap with that page's title and first eight headings; links with no matching terms are skipped. It directly navigates to at most five matching public link destinations with mediated GET requests. This is a bounded text heuristic and does not establish semantic relevance. The worker does not click links, fill forms, or run page JavaScript. Redirected subresources fail closed. Search, navigation, and page resources use GET only; the search workflow is bounded to five provider destinations plus five discovered links, subject to the shared request, response-byte, and runtime limits.

After page extraction, the host sends at most 16 KiB of UTF-8 excerpts and the validated citation list through the task capability bridge to Django. Django sends only the user's question, those excerpts, and the verified sources to the exact model route captured when the chat turn began. It sends no conversation history, saved memory, tools, or model credential. The prompt marks all page text as untrusted. The model has a 75-second total wall-clock deadline and 12 KiB answer limit; Django rejects source IDs outside `[1]` through `[N]` and any URL not in the opened source set. The bridge stores a fingerprint and result state per run, replays a completed result without a second model call, and fails closed on a timeout or model error. Page excerpts are transient bridge data and are not written to the worker spool or artifacts.

The search browser session has a 240-second worker timeout, a maximum 120-second post-publication session TTL, a 110-second host bridge wait, and a 125-second browser-to-host request timeout. This leaves bounded time for synthesis and then owner inspection; changing any of these limits requires rerunning the Docker integration check.

The synthetic Docker integration verifies the successful approval-to-answer flow, one shared-ledger reservation, a two-hop main-frame redirect, matching direct-GET link traversal, a successful third-party stylesheet GET, a blocked private destination, a redirected stylesheet whose target is never requested, UTF-8 byte truncation, model synthesis, and verified citations. Chat-to-host tests separately verify expiry before any query/provider/browser request and report a synthetic Mwmbl 503 without starting the browser. Deployment-wide ledger configuration remains pending. Live Mwmbl availability is separate from these controlled fixtures.

## Optional owner sign-in handoff

The owner can separately opt in to a manual sign-in handoff for one browser task. The initial URL, every main-frame and subresource request, and every redirect in this mode must use HTTPS; the approval endpoint, worker, route handler, and host mediator all enforce this. HTTP URLs remain available only in the separate non-handoff GET-only mode. JavaScript and WebSockets remain disabled. The owner controls a pointer and keyboard through an owner-only, CSRF-protected panel. Typed strings, command events, and live JPEG frames stay in bounded process-memory queues and the live BrowserContext; they are not written to the skill spool, application logs, artifacts, or model input. The host bridge is limited to the configured loopback Django port and a short-lived capability bound to the task and owner.

During control, the page adapter permits GET requests and a main-frame URL-encoded POST only after either a direct owner click/Enter or the fixed adapter's one-shot form preparation. A recognizable username/password POST uses the sign-in path. For an explicit action request attached to one public URL task, after the owner enables HTTPS handoff and takes control, the selected chat model can prepare values for visible text/email/URL/search/telephone/textarea fields from bounded form metadata. Labels and page text sent to the model are marked untrusted; no current field values, credentials, cookies, or hidden values are sent. The adapter fills the values with page JavaScript disabled, captures the filled page for owner inspection, and submits to the mediator, which pauses the exact POST until the owner reviews the destination, labels, summary, and safe submitted values in the owner-only panel. The host binds the one-use owner decision to the immutable request digest and dispatches only after approval. Payment, purchase, transfer, stored payment/card markers, credentials, unsupported encodings/fields, unclear plans, and non-HTTPS destinations fail closed. Page content is untrusted and cannot approve an action. This classifier cannot establish every site's semantics, so the owner must inspect the page and proposal. Only one form and one action can be prepared in a handoff session; arbitrary methods, JavaScript-dependent or multipart forms, and unclear effects are unsupported. `Set-Cookie` is handled in the volatile BrowserContext and is not copied to the page result or application storage. When the owner returns control, the adapter clears the in-memory handoff, reads page title and visible text, removes owner-typed values from that text in both the browser and host worker, strips query and fragment components from source citations, and only then publishes the sanitized result. A separate unchecked consent lets the owner send that visible page text and the original user request to the selected model route for a bounded continuation. Without that opt-in, no authenticated page text is sent to the model. Credentials, cookies, screenshots, and values typed during sign-in remain excluded. The continuation is a single synthesis response; it does not resume browser tools or claim unsupported actions.

This handoff does not support JavaScript-dependent sign-in, SPA flows, MFA or one-time codes, arbitrary form encodings, payment/card activity, or redirected subresources. Unsupported and uncertain requests fail closed. Screenshots and artifacts are disabled for every task with handoff enabled, including direct endpoint calls. The live browser container and context are closed at task completion; cancellation clears the process-memory handoff, and worker recovery removes the container and clears the bridge before ending consent. The synthetic agent-prepared chat-to-action flow is documented in `docs/issue-70-validation.md`; it does not prove production behavior or rollback of website changes.

Refresh these as a reviewed unit, rebuild both skill images, and rerun the browser mediator and Docker isolation tests before deployment.

## Build and controlled validation

With Docker Desktop available:

```powershell
docker build --target skill-worker -t superharry-skill-worker:local .
docker build --target skill-browser-worker -t superharry-skill-browser-worker:local .
```

The normal provisioning/deployment helper builds the dedicated browser image whenever skill spool support is enabled. Browser acceptance uses controlled page fixtures through a test mediator, and separately tests absolute/relative public redirects, redirect loops and limits, private/non-HTTP destinations, private-address rejection, non-GET rejection, and direct-egress denial from a `--network=none` container. Docker Desktop checks do not establish deployment or live-provider acceptance.
