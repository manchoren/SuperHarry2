# Issue #67: Mwmbl provider evidence

## Status and boundary

Issue #67 was closed after the resolution evidence was posted to GitHub. Mwmbl search is wired into the owner-approved Playwright task: after consent, the host worker calls Mwmbl through the mediated GET path, applies the shared SQLite limiter, and passes up to five validated result URLs into the isolated browser. The browser opens those pages through the mediator, follows safe main-page redirects, and ranks up to 20 visible anchors per opened result page by matching their labels against that page's title and first eight headings. It directly navigates with GET to at most five matching public links; no-click or page-JavaScript behavior is used. Zero-overlap navigation links are skipped. This is a simple lexical relevance filter, not a semantic relevance guarantee. Django sends bounded excerpts to the exact chat model route selected for the original turn and returns a synthesized answer with the worker-verified source list. Mwmbl result titles and snippets are not displayed.

Before approval, the owner sees the search question, Mwmbl and its CC BY-NC-SA 4.0 license, and a disclosure that opened-page excerpts will be sent to the selected chat model. The synthesis request contains only that question, bounded excerpts, and verified source URLs; it includes no full conversation, saved memory, tools, or model credentials. Page text is marked untrusted. Answers must cite IDs from `[1]` through the verified source count; zero/out-of-range IDs and URLs outside the verified source set fail the task. A per-run digest and persisted status prevent repeat model calls after retries. The answer request has a 75-second wall-clock limit; timeout, gateway exceptions, empty output, or invalid citations persist a failure and do not claim a synthesized result.

The Docker end-to-end fixture exercises chat approval through the host worker and browser bridge, configured SQLite ledger, a two-hop redirect, relevance-ranked GET navigation to a discovered public link, private-destination refusal by the synthetic mediator, model synthesis, citations, and owner reply. Separate chat-to-host-supervisor fixtures verify that an expired approval makes no bridge/provider/browser request and that an Mwmbl HTTP 503 is reported without launching the browser or fabricating an answer or citations. These are local synthetic checks, not live-provider or deployment evidence. Deployment-wide ledger configuration remains unverified. Redirected subresources remain blocked by the accepted scope.

The owner selected Mwmbl with its advertised anonymous-tier limits and accepted the published terms discrepancy and license. The host worker reads `WEB_SEARCH_PROVIDER` (currently only `mwmbl` is implemented) and optional `MWMBL_SEARCH_ENDPOINT` from its environment; the endpoint must pass HTTPS validation and all traffic still uses the mediator. `configured_mwmbl_limiter` fails closed unless the host operator configures `MWMBL_SHARED_LEDGER_DIRECTORY` as an absolute local-host path. Provider and limiter unit tests use local synthetic responses; they do not contact Mwmbl.

## Provider and terms evidence

Mwmbl's [developer page](https://developer.mwmbl.org/) documents the endpoint `https://api.mwmbl.org/api/v2/search/?q=...`. It advertises an anonymous tier with no sign-up or API key, limited to 1,000 requests per month and one request per second, tied to the source IP. This means users sharing SuperHarry's egress address would share that anonymous quota and rate limit. The same page offers a separate key-based tier; this implementation does not use a key or enable a paid tier.

The [API terms](https://developer.mwmbl.org/terms/) say in the API Access and API Keys section that access requires an account and API key, while the same page lists an Anonymous plan and the developer page says no key or sign-up is needed. This remains an unresolved discrepancy between Mwmbl's own published pages; the live anonymous request below shows current endpoint behavior but does not settle the contractual wording.

The anonymous tier's one-request-per-second limit and 1,000-request monthly quota are tied to the source IP. They are shared by every SuperHarry user and worker that exits through the same public IP. The current supported topology routes browser/container requests through the host mediator; the browser container has `--network=none`, Django has no Docker socket, and the operator runs `scripts/run_skill_jobs.py` on the host. `lock_spool` rejects a second worker process for the same spool, but does not coordinate separate spools. The host-only `MWMBL_SHARED_LEDGER_DIRECTORY` setting lets workers with separate spools on the same host use one SQLite quota ledger; `configured_mwmbl_limiter` refuses to fall back to a per-spool ledger. Every dispatcher sharing an egress IP must use that same local directory and run its calls inside the host worker's serialized dispatch path. SQLite transactions then serialize its quota and rate reservations across those local processes. This setting cannot detect or coordinate a worker that omits the setting, another host, or separate filesystems. Therefore Mwmbl search must fail closed unless the operator can guarantee all dispatchers for an egress IP use the same shared local-host ledger. The application is integrated with the approved browser-task flow, but local fixture tests do not establish deployment-wide ledger configuration or live-provider acceptance.

### Limiter runtime and storage assumptions

- `mwmbl-usage.sqlite3` lives in the operator-configured shared host-side ledger directory, not implicitly in a skill spool. `configured_mwmbl_limiter` fails closed when `MWMBL_SHARED_LEDGER_DIRECTORY` is missing, relative, or unavailable. SQLite transactions serialize reservations among processes using that same local file and `synchronous=FULL` is requested. Monthly attempts are committed before injected transport starts, so a crash or provider failure remains charged. Corrupt state, I/O errors, quota uncertainty, and a UTC clock moving backwards fail closed.
- The clock source is the host wall clock interpreted as UTC. Forward month changes reset monthly attempts; a backwards month or backwards dispatch timestamp blocks requests. The persisted next-allowed timestamp preserves the one-second gap across process restarts. An in-flight marker left by process termination causes the next call to wait one full second before recovering.
- The dispatch path must remain inside `scripts/run_skill_jobs.py:supervise`'s `lock_spool(spool)` context. That process-wide worker lock excludes a second host worker for the same spool; SQLite reservations additionally coordinate same-host workers on different spools only when all use the identical `MWMBL_SHARED_LEDGER_DIRECTORY`. The Linux browser container does not dispatch Mwmbl directly; it asks the host mediator. A separate host with the same public egress IP cannot be coordinated by this local file and must not dispatch Mwmbl.
- Cross-OS locking was probed anyway on a Docker Desktop bind mount and did not work: Windows `msvcrt.locking` did not conflict with Linux `fcntl.flock`; SQLite `BEGIN IMMEDIATE` also did not coordinate in either direction (host-held then Linux got the lock in 0.003 seconds; Linux-held then Windows got it in 0.000 seconds). Therefore, the shared ledger must remain on the host and all dispatches must go through host processes. If a future design permits the Windows host and Linux container to dispatch directly, or permits multiple hosts behind one egress IP without a truly shared quota service, this limiter is invalid and must be replaced before enabling provider access.
- Three independent Windows Python subprocesses on a local SQLite file serialized `BEGIN IMMEDIATE` transactions (all exit 0; transaction-start gaps were 0.257s and 0.322s when each held a transaction for 0.25s). The unit tests also verify that `lock_spool` rejects a second worker process, preserves usage across limiter restart, enforces quota/pacing, and recovers a crashed reservation. This does not establish cross-OS lock support.

The API terms also state that the service is best-effort, has no uptime or continuity commitment, and may be changed, suspended, or discontinued. Failures and quota/rate responses therefore must be shown as provider failures; they must not be turned into fabricated search results.

Mwmbl states that search results are made available under [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/) and remain subject to rights held by original content owners. Titles, result URLs, and snippets must be treated as externally sourced material. If the UI displays Mwmbl-provided titles or snippets, it must visibly attribute Mwmbl and link the CC BY-NC-SA 4.0 license. Text fetched from a selected result page must instead be attributed to that original page URL; do not imply Mwmbl owns or licensed the destination page text. The eventual search-to-answer flow must preserve both kinds of attribution where applicable and comply with the license conditions; this adapter does not grant reuse rights or decide whether a particular deployment's use qualifies as noncommercial.

## Accepted runtime boundary and operational limits

- The owner approved GET-only search: the worker follows matching public links by direct mediated GET navigation without clicks, forms, or page JavaScript. The relevance filter is lexical overlap with page titles and headings, not a semantic relevance guarantee.
- Main-page redirects are followed and revalidated through the host mediator. Direct public subresources use GET; redirected subresources are blocked as explicitly accepted. Public sites can still attach effects to GET; known payment/card/action markers are rejected, but arbitrary state-changing GET semantics cannot be fully classified.
- Only successfully opened page URLs are cited. Search-result titles/snippets are not displayed; page text is untrusted and synthesized answers cite the original opened page URLs.
- The host worker remains the only Mwmbl dispatcher and uses the shared SQLite limiter. `MWMBL_SHARED_LEDGER_DIRECTORY` must point to the same host-local directory for every dispatcher sharing an egress IP; the provider fails closed when it is missing or unusable. The local Docker checks do not prove deployment-wide coordination or live-provider availability.
